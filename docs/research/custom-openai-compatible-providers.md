# Custom OpenAI-compatible providers and model discovery

Research date: 2026-11-09. Scope: [Mivra issue #69](https://github.com/okhay-p/mivra/issues/69). Research and recommendations only; this note does not amend an ADR or approve an open decision.

## Recommendation

Persist non-secret provider configuration in SQLite settings; keep keys in the existing private credential store outside the database. Start with provider name, API base URL, key, a model selector with **Refresh models**, and **Enter model ID** available regardless of discovery success. Discover with server-side `GET <baseURL>/models`. Do **not** add a custom model-list URL in the first version: both motivating services have a conventional model-list path today, and manual IDs cover unavailable or unusual catalogs. Use Chat Completions explicitly for custom providers initially; discovery success does not establish streaming, tool calling, Responses support, or reasoning compatibility. These are recommendations inferred from the evidence below, not accepted decisions.

## Mivra constraints and current code

- [ADR-012](../adr/0012-model-picker.md) requires one app-wide model/effort selection, namespaced model provenance, and a tool-capable catalog. [ADR-013](../adr/0013-distribution-and-api-keys.md) keeps API keys outside SQLite and gives environment keys precedence. Its env-only URL restriction is still in the file, but the [owner's issue comment](https://github.com/okhay-p/mivra/issues/69#issuecomment-6732686225) explicitly approves UI-editable URLs, including overriding environment URLs. Persistence and discovery remain undecided. Preserve the loopback-only credential-write rule unless separately approved.
- [ADR-015](../adr/0015-sign-in-with-chatgpt.md) fixes the ChatGPT token destination to OpenAI. Custom provider URLs must never affect that path or receive built-in provider credentials.
- Inspected Mivra checkout: `e15d3899397d63590396bce9247351eafbd37709`. [config.ts](../../packages/server/src/config.ts) handles deployment settings; [start.ts](../../packages/server/src/start.ts) captures direct-provider environment base URLs and builds catalogs/registries. [model.ts](../../packages/server/src/model.ts) registers a fixed provider set. Its generic OpenAI registry uses `createOpenAI`, whose installed SDK `languageModel` implementation creates Responses models. A new URL alone therefore does not provide a Chat Completions integration.
- [catalog.ts](../../packages/server/src/models/catalog.ts) already appends `/models` for OpenAI discovery, caches last-good lists, and intersects direct model IDs with OpenRouter metadata. That intersection would exclude arbitrary custom models. [selection.ts](../../packages/server/src/models/selection.ts) validates selections against the catalog. Custom manual entries must become catalog entries without requiring an OpenRouter counterpart.
- [settings-store.ts](../../packages/server/src/store/settings-store.ts) already persists JSON settings. [credentials.ts](../../packages/server/src/credentials.ts) writes `credentials.json` atomically with mode `0600`, but exposes a fixed provider-ID union. Custom credential references need their own stable provider identity. [key-check.ts](../../packages/server/src/models/key-check.ts) currently probes lists/authentication without inference; it cannot satisfy #69's streaming/tool test by itself.

### Protocol and metadata are independent of discovery

- Cline's inspected compatible transport explicitly uses `createOpenAICompatible`; its native OpenAI transport uses `provider.responses`. This is an intentional transport distinction. [compatible source](https://github.com/cline/cline/blob/94eecbbe1a2f899c66b118d13656651b0a884e1f/sdk/packages/llms/src/providers/vendors/openai-compatible.ts), [native source](https://github.com/cline/cline/blob/94eecbbe1a2f899c66b118d13656651b0a884e1f/sdk/packages/llms/src/providers/vendors/openai.ts)
- Continue docs describe Responses for certain OpenAI models and `useResponsesApi: false`. The inspected adapter further restricts automatic Responses selection to the official OpenAI API base, so a matching model name on an arbitrary server is insufficient. [docs](https://docs.continue.dev/customize/model-providers/top-level/openai), [adapter source](https://github.com/continuedev/continue/blob/5522c6f44ca0ac3528b37244818fbfa39b5af470/packages/openai-adapters/src/apis/OpenAI.ts#L90)
- Standard OpenAI model objects provide identity/creation/ownership fields, not a complete context-window, tools, vision, pricing, and effort contract. [OpenAI list reference](https://developers.openai.com/api/reference/resources/models/methods/list) Continue consequently exposes explicit capabilities and context/output limits; Cline exposes model overrides. [Continue reference](https://docs.continue.dev/reference), [Cline docs](https://docs.cline.bot/provider-config/openai-compatible)
- OpenCode's documented defaults for unknown configured models are assumptions, including tool/image support and token limits; users can override capabilities and limits. They are not discovery results. [model configuration docs](https://opencode.ai/docs/models#aliases) Mivra should retain unknown metadata as unknown instead of inferring capabilities or effort from model spelling. Provider-specific extensions can enrich a list, but their shapes are not universal.

## Motivating services verified

### DeepSeek

DeepSeek's own current quickstart specifies OpenAI base `https://api.deepseek.com` and demonstrates `/chat/completions`; current model IDs include `deepseek-flash` and `deepseek-v4-pro`. Its model-list reference specifies `GET /models`, so the documented combination is `GET https://api.deepseek.com/models`. Do not substitute model IDs from another tool's older examples. [DeepSeek quickstart](https://api-docs.deepseek.com/)

The current list schema is richer than a minimal OpenAI list: optional display name, context window, output limit, modalities, effort levels and per-protocol capabilities. Fields can be omitted. Thus “DeepSeek returns only IDs” is not accurate for today's documented API. [DeepSeek model-list schema](https://api-docs.deepseek.com/api/list-models/)

DeepSeek also now documents `POST /responses`. It is stateless, requires conversation history to be resent, and treats developer messages as user messages. Availability of this endpoint does not mean complete behavioral equivalence to OpenAI Responses. Chat Completions remains the simpler first integration surface. [DeepSeek Responses reference](https://api-docs.deepseek.com/api/create-response/)

No authenticated DeepSeek listing/inference was performed. A direct unauthenticated GET to `/models` returned HTTP 401 on the research date; actual account-specific inventory and streamed tool behavior remain untested.

### OpenCode Go

Current official docs give Go service root `https://opencode.ai/inference/go`, with Chat Completions suffix `/openai/v1/chat/completions` and Responses suffix `/openai/v1/responses`. Therefore Mivra's **API base** for conventional OpenAI paths should be `https://opencode.ai/inference/go/openai/v1`. The Go/harness docs say text models can be translated across API families. The general inference page still emphasizes native families, so native routing and translated routing should be distinguished. [harness base URLs](https://opencode.ai/docs/console/harnesses#base-urls), [Go endpoints](https://opencode.ai/docs/console/go/#endpoints), [inference reference](https://opencode.ai/docs/console/api/inference)

Direct unauthenticated GET observations on 2026-11-09 (no redirects followed, no inference):

| First-party URL | Observed response |
| --- | --- |
| [General inventory](https://opencode.ai/inference/v1/models) | HTTP 200, JSON `data` list, 81 entries. This is the live-list URL documented by the inference reference. |
| [Go inventory](https://opencode.ai/inference/go/v1/models) | HTTP 200, JSON `data` list, 30 entries. |
| [Go OpenAI-base inventory](https://opencode.ai/inference/go/openai/v1/models) | HTTP 200, JSON `data` list, 30 entries. **The default `<baseURL>/models` algorithm works here today.** |

Go entries included optional `canonical_id`, `capabilities`, `limit`, `cost`, and API-specific base URLs/SDK hints. One observed entry was `deepseek-v4.1-flash`; it is a Go model ID, distinct from DeepSeek's direct-service alias. Public inventory is not proof of account entitlement or inference success. Counts and extension fields are observations, not a stable API promise. The browser fetch tool could not render the live JSON URL; direct HTTPS GETs succeeded.

Go's docs require a stable session header (`x-opencode-session`) and describe expected coding-agent traffic and client identification. Mivra is a learning harness: technical compatibility does not establish that Go is appropriate for this workload. Confirm suitability and header requirements before advertising Go as validated. [Go client requirements](https://opencode.ai/docs/console/go/#where-can-i-use-it), [session requirements](https://opencode.ai/docs/console/harnesses#sessions)

OpenCode the client also has a dedicated Console integration fetching `/api/v2/config`; its built-in Go experience must not be mistaken for generic custom-provider `/models` behavior. [integration source](https://github.com/anomalyco/opencode/blob/fee1ca5aa9e1d62a7ca42ef7eeaa8c02fe6ed080/packages/core/src/plugin/provider/opencode.ts#L576)

## Proposed Mivra behavior

These are design recommendations, not descriptions of existing code:

1. **Persistence:** store stable provider ID, display name, base URL, configured model IDs, optional metadata overrides and discovery preference in SQLite settings. Reference keys by stable provider ID in the private credential store. A rename must not change model identity. Explicitly saved URL > environment URL > built-in default; offer a reset to the environment/default and show the effective source. Key precedence stays env > credential store. Reject URL user-info and secret-bearing query parameters; simplest initial rule is no query or fragment. URLs stored as non-secrets must contain no credentials.
2. **Simple setup:** name, API base URL (including version prefix), key, and model choice/manual IDs. Explain that users enter the base, not a full `/chat/completions` URL. Normalize trailing slashes and append paths without dropping a custom path prefix. Do not silently guess `/v1` or probe several destinations with credentials.
3. **Discovery:** a refresh makes a bounded server-side GET to `<baseURL>/models`, using only that provider's credentials. Parse the conventional `data[].id` list; validate/deduplicate IDs and bound response size/count/time. Show actionable authentication, timeout, unexpected-format and endpoint errors. Keep manual entries usable and last-good discovery visibly stale. Invalidate discovery and verification when URL/key changes; never reuse an old endpoint's success for a new one.
4. **Compatibility test:** separately test the selected model with a small streamed tool call and tool-result continuation. Report discovery and inference results separately. A successful list call proves neither credential validity on a public catalog nor Mivra compatibility. Avoid enabling unsupported reasoning parameters; omit them by default. A small test establishes a baseline, not universal reliability on every tutor turn.
5. **Metadata:** IDs without an OpenRouter match remain selectable. Context, output limit, price and effort can be unknown. Expose optional context/output overrides under Advanced when useful; do not invent prices, image support or effort ranges. If metadata-based tool filtering is impossible, distinguish unverified models from models that pass the streaming/tool test. Any operational context budget needed later must be an explicit Mivra policy, not presented as the provider's capacity.
6. **Isolation/lifecycle:** custom requests use an explicit Chat Completions adapter and only the custom key. Keep ChatGPT's fixed Responses route isolated. Apply the existing local-write restrictions to endpoint changes because changing a destination can disclose its associated credential. Reject redirects on credentialed requests, and preserve useful sanitized errors. Refresh catalog/registry on configuration changes, retain namespaced provenance, and offer a clear picker recovery when the selected provider is removed. Do not silently switch models mid-run.

### Is a custom model-list URL worth adding?

**Defer it.** A second URL cannot fix missing streaming/tools or API incompatibility. It adds another destination, auth-scope rules, response-format expectations, validation and cache identity. DeepSeek and Go already work with the conventional path at the documentation/GET level; Cline and Open WebUI demonstrate manual fallback. Manual IDs meet #69 even when discovery fails.

Revisit only after a real supported service has a valuable separate catalog that users cannot reasonably enter manually. Then make it an optional Advanced **Model list URL**, blank meaning `<baseURL>/models`, with an explicit supported response schema. Default cross-origin catalog requests to no credentials; any authenticated alternative needs a separately resolved credential policy. Do not build configurable JSON extraction, alternate auth, or automatic endpoint chasing without a demonstrated requirement. A stable per-session header for Go is a separate compatibility question, not a reason for a model-list URL field.

## Open decisions and limitations

- Owner approval covers UI URL editing/overrides only. Persistence, initial protocol scope, metadata/verification policy and ADR-012/013 amendments still need resolution; no ADR was edited here.
- Decide whether setup requires a passing compatibility test or permits saving an explicitly unverified configuration, and whether multiple configured model IDs are individually verified. Discovery failure alone should never prevent manual entry.
- Decide initial metadata overrides and handling of changed endpoints under the same provider ID, including replay/provenance implications. Provider IDs distinguish services, but an edited destination may have different model behavior under the same model ID.
- Confirm Go's suitability for learning traffic and required headers. No paid inference, authenticated DeepSeek call, entitlement check, or end-to-end Mivra integration test was performed.
- Compared current official docs and pinned source, not installed-release behavior for every platform. Continue has multiple request paths; Cline's inspected paths are the VS Code UI/controller and SDK transport. Local discovery adapters and provider-specific rich metadata should not be generalized to all compatible services.
- Only this Markdown note was added. No tests were run for this docs-only research; no implementation, issue changes, PR, or Notion updates were made.
