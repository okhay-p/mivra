# Developing Mivra

How to run Mivra from source, test it, and how its parts work. For installing and using Mivra, see the [README](../README.md). Releases are covered in [`releasing.md`](releasing.md), and design decisions in [`adr/`](adr/README.md).

## Layout

| Package | What it is |
|---|---|
| `packages/server` | Hono API server (Node.js). Owns the agent runtime, the SQLite database (Drizzle + better-sqlite3) and model access (Vercel AI SDK). Binds to `127.0.0.1` only. |
| `packages/web` | React + Vite web UI (shadcn/ui on Tailwind v4). Talks to the server only through its API. |
| `packages/mivra` | The installable `@okhay-p/mivra` package and its `mivra` command (ADR-013): the server, protocol and built UI bundled into one npm package, with `start`, `stop`, `status` and `auth`. |
| `packages/protocol` | Versioned Zod schemas for learning artifacts (`algorithm_trace`, `code_exercise`, `code_walkthrough`, `composition`, `set_diagram`, `graph`, `multiple_choice`, `table`, `worked_steps`), their tool definitions, the deterministic graders and the QuickJS and Pyodide case runners that code exercises share between server and browser. Shared by server and web. |

## Setup

Requires Node.js 22.14+ and pnpm 10 (`npm i -g pnpm`, or prefix commands with `npx pnpm@10`).

```sh
pnpm install
```

Models run through [OpenRouter](https://openrouter.ai), Anthropic or OpenAI, so one API key is the only setting needed: an OpenRouter key reaches every model, while Anthropic and OpenAI keys call those providers directly. Add a key in the app under **Model providers** in the sidebar, which opens by itself while no key is set. Keys saved there go in `credentials.json` in the data dir (mode 0600), never in the database, and are never sent back to the browser; **Check** asks the provider whether it accepts the key, without spending tokens. Only a browser on the computer running Mivra can change keys: requests through a proxy such as `tailscale serve` see them read-only (ADR-013). `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` in the environment or `.env` (see `.env.example`) still work and take precedence over saved keys. A new or removed key applies from the next reply, without a restart. Until you choose a model, a new install uses GPT-6 Luna at high effort: through OpenRouter if its key is set, otherwise through OpenAI. With only an Anthropic key, it uses Claude Sonnet 5.5 (ADR-012). `MIVRA_MODEL` and `MIVRA_REASONING_EFFORT` are no longer read, and the server warns at startup if they're still set.

Instead of a key, a learner with a ChatGPT Plus or Pro plan can **Sign in with ChatGPT** under Model providers (ADR-015). The server starts the OAuth flow (`packages/server/src/chatgpt/`), listens on `127.0.0.1:1455` (or any free port) for the browser to come back, and keeps the tokens in `chatgpt.json` in the data dir (mode 0600, never in the database or the browser). ChatGPT models appear in the picker as `chatgpt:<slug>` and call `https://api.openai.com/v1/responses` with `store: false`; the access token is renewed before a run when it has under five minutes left. When signed in, the built-in default is GPT-6 Luna through ChatGPT. Unlike keys, a browser on another machine (over `tailscale serve`, say) can sign in too: ChatGPT sends it back to its own `127.0.0.1`, which fails, and you paste that address into the panel. `mivra auth login chatgpt` does the same from a terminal. The UI follows OpenAI's Sign in with ChatGPT guidelines: the "Continue with ChatGPT" button, "Using ChatGPT plan" with **Manage usage** beside the model picker, a usage-limit notice, and a one-time welcome dialog. Tests use a fake authorization server (`packages/server/test/chatgpt.test.ts`); nothing in the suites calls OpenAI.

**OpenAI-compatible providers** (issue #69) can be added under Model providers for any service with an OpenAI-compatible Chat Completions API, such as a local server: a name, the API base URL (including any version prefix, never the `/chat/completions` address), an optional key and model ids. **Refresh models** loads `GET <base URL>/models` (10 s, 4 MB, 2,000 ids at most); ids can always be typed in by hand, and a failed refresh keeps the last good list marked stale. **Test model** makes a small streamed call that must call a tool and continue after its result (`packages/server/src/models/custom-providers.ts`); untested models can still be selected. Each provider gets a stable id from its first name, and its models are `custom:<id>/<model id>`. The configuration is in the `settings` table and the key in `credentials.json` under `custom:<id>`. `MIVRA_PROVIDER_<ID>_BASE_URL` and `MIVRA_PROVIDER_<ID>_API_KEY` set them from the environment; a URL saved in the UI wins over the environment's, while an environment key wins over a saved one. Changing one applies from the next run, and a new URL or key clears that provider's list and test results. Requests carry only that provider's key, stay under its base URL and never follow redirects. Tests use a fake compatible service (`packages/server/test/support/fake-compatible.ts`), which the e2e harness also serves at `/e2e/compat/v1`.

The picker under the message box chooses the main model and reasoning effort for every later reply and syllabus, and for lessons unless Settings → Models overrides it; a reply already streaming keeps its model. It lists the models that can call tools, which Mivra's learning tools need, from each provider whose key is set, plus the default model. OpenRouter's public list describes every model (name, price, effort levels and tool support), so Anthropic's and OpenAI's own models appear only when OpenRouter lists their counterpart. The lists refresh hourly, and a saved copy is used offline. Search results are grouped by provider, and a model called directly shows its provider next to its name. Opened, it shows your pinned and recent models and a few suggestions; typing searches the whole list. The star pins the current model. The effort menu shows only the levels the selected model supports. Each reply names the model that wrote it, and each run records its model and effort. Reasoning details from earlier replies go back only to the model that wrote them, so after a switch the new model sees earlier replies as text.

**Settings → Models** (issue #71, ADR-012 option D) can give a background task its own model and effort; for now the only task is lesson generation. A task uses the main model until overridden, following any later change to it, and **Use main model** removes the override. Overrides are checked like the main selection and saved in the `settings` table (`model.task.<task>`; API: `GET /api/settings/tasks`, `PUT` and `DELETE /api/settings/tasks/{task}`). Each job reads its model when it starts (`forTask` in `packages/server/src/app.ts`) and keeps it to the end, and its run records it. An override that can't run fails the lesson with a message and a link to Settings instead of using another model.

## Commands

| Command | What it does |
|---|---|
| `pnpm dev` | Server on :4096 with reload, plus Vite on :5173 proxying `/api` to it |
| `pnpm build && pnpm start` | Production: the server serves the built web UI on :4096 (no port fallback; the `mivra` command has one) |
| `pnpm test` | Protocol, server API (mock model, no API key needed) and web component tests (Vitest + jsdom) |
| `pnpm test:e2e` | Chromium browser tests: built UI and real server with a scripted model; no API key. Install with `pnpm --filter @mivra/e2e exec playwright install chromium`. Runs on up to 4 workers (`MIVRA_E2E_WORKERS`), each with its own server and database. A run uses the ports from `MIVRA_E2E_PORT` (default 4198) to that plus the worker count minus one, so give concurrent runs separate blocks |
| `pnpm test:e2e:all` | Full browser suite, including graph tests in Firefox and WebKit. Required for graph, layout, font or keyboard changes. Install with `pnpm --filter @mivra/e2e exec playwright install chromium firefox webkit` |
| `pnpm test:changed [ref]` | Only the Vitest tests affected by changes since `ref` (default `origin/main`), in every package: those that import a changed file, directly or not. Most server tests import the whole app, so a server change still runs most of them; a change elsewhere skips the packages it doesn't reach. Tests that run code in another process aren't traced, such as `packages/mivra`'s CLI tests, which start the built `mivra`: after changing `packages/mivra/src`, run `pnpm --filter @okhay-p/mivra test` too |
| `pnpm typecheck` | Type-check all packages |
| `pnpm --filter @mivra/server db:generate` | Generate a migration after editing `src/db/schema.ts` |

`pnpm test`, `pnpm test:changed`, `pnpm test:e2e` and `pnpm test:e2e:all` run through `scripts/test-slot.mjs`, which lets one test run at a time use the machine, across every worktree. The others print that they're waiting and start when it's done. The suites are CPU-bound, so runs that overlap only slow each other down, and tests that wait on timers or other processes start timing out. Each run holds a slot by listening on a loopback port (4180 upwards, `MIVRA_TEST_SLOT_PORT`), which the system frees however the run ends. `MIVRA_TEST_SLOTS=2` allows two runs at once and gives each its share of the CPUs (`MIVRA_TEST_WORKERS` for Vitest, `MIVRA_E2E_WORKERS` for Playwright), and `MIVRA_TEST_SLOTS=0` turns the wait off. Running Vitest or Playwright directly in a package skips the wait.

On GitHub, `.github/workflows/test.yml` runs typecheck, the build, each package's unit tests and the whole e2e suite on every pull request and every push to `main`, with the slot turned off and the Chromium specs split across three runners. Its **Tests passed** check is what a PR needs to merge. Locally, run `pnpm typecheck` and `pnpm test:changed` while you work, plus the e2e specs you touched; the workflow runs the rest.

Workspace packages resolve to their TypeScript source in dev, tests and type-checking through the `@mivra/source` export condition, so `pnpm dev` needs no prebuild. `pnpm build` compiles `packages/protocol` first; the production server loads its `dist`.

The pnpm patch for `@openrouter/ai-sdk-provider@3.1.0` handles a discarded stream-cancellation rejection that can exit Node after a client disconnect. Remove it when an upstream version handles that rejection and passes `packages/server/test/openrouter-exit.test.ts`.

Data is stored in `~/.mivra/mivra.db` (override with `MIVRA_DATA_DIR`). The API's OpenAPI document is at `/api/doc`.

## The `mivra` command

`packages/mivra` builds `@okhay-p/mivra`, the package people install with `npx @okhay-p/mivra` (ADR-013). npm refused the unscoped name `mivra` as too similar to `micro`; the command it installs is still `mivra`. `pnpm build` at the root builds it last: esbuild bundles the CLI with the server, `@mivra/protocol` and the patched OpenRouter provider into `dist/`, and copies the migrations and built UI next to it. The build fails if the bundle imports a package that isn't in its `dependencies`, or lists one it never imports. Try it from the repo with `node packages/mivra/bin/mivra.js`, or test the real install with `npm pack` in `packages/mivra` and `npm install ./okhay-p-mivra-<version>.tgz` in an empty folder.

| Command | What it does |
|---|---|
| `mivra` / `mivra start` | Starts Mivra in the foreground (Ctrl+C stops it) and opens the browser. Port 4096, or the next free one up to 4115 when it's taken. `--port <n>` (or `MIVRA_PORT`) asks for one port and fails if it's taken. `--no-open` skips the browser. Says so and opens the browser if Mivra is already running |
| `mivra start --detach` | Runs it in the background, logging to `mivra.log` in the data dir, and returns once it answers |
| `mivra stop` / `mivra status` | Stops the Mivra recorded in `mivra.pid` (after checking it answers as Mivra, so a reused pid is never signalled), or says where it runs |
| `mivra auth set <provider>` | Saves an API key to `credentials.json`, read from a hidden prompt or a pipe, never from an argument, then checks it with the provider (`--no-check` skips that). Providers: `openrouter`, `anthropic`, `openai` |
| `mivra auth status` / `mivra auth remove <provider>` | Lists where each key comes from, or removes a saved one. A running Mivra picks changes up from the next reply |
| `mivra auth login chatgpt` / `mivra auth logout chatgpt` | Signs in with ChatGPT (opens the browser, or prints the address with `--no-open`, and accepts the address the browser ends on pasted back; `--new-account` registers a different account), or signs out and revokes the session |
| `mivra import obsidian <folder>` | Reads the vault's `.md` files on this machine, skipping hidden folders and symbolic links, and sends them to the Mivra recorded in `mivra.pid` with the token from `auth-token`. An import with the same name (`--name`, default the folder's name) is re-imported instead. A server from `pnpm dev` has no `mivra.pid`, so use the API there |

Before applying new migrations to a database that already has data, the server copies it to `backups/mivra-<time>.db` next to it (`VACUUM INTO`, so the copy is consistent) and keeps the newest 5. If the copy fails, nothing is migrated. A database last migrated by a newer Mivra is refused with a message instead of being opened, since older code can't safely use it; restore a backup or update Mivra. `bin/mivra.js` checks for Node 22.14+ before loading anything else, and a `better-sqlite3` that can't load points to the Docker image. `pnpm build` also copies `LICENSE` into the package and writes `THIRD_PARTY_NOTICES.md` from the licenses of the code bundled into it (the web UI's production dependencies and the inlined server packages).

## Docker

`docker/Dockerfile` builds an image of the published npm package on `node:22-bookworm-slim`. It runs as the unprivileged `node` user, keeps its data in the `/data` volume and has a health check. It's published to GitHub Container Registry as `ghcr.io/okhay-p/mivra`:

```sh
docker run -d --name mivra --restart unless-stopped \
  -p 127.0.0.1:4096:4096 -v mivra-data:/data \
  -e OPENROUTER_API_KEY=sk-or-... \
  ghcr.io/okhay-p/mivra
```

Then open <http://127.0.0.1:4096>. Inside the container the server listens on all interfaces (`MIVRA_HOST=0.0.0.0`), since a published port can't reach the container's loopback. `-p 127.0.0.1:…` keeps it on the host's loopback. Expose it beyond that only on purpose, with `MIVRA_ALLOWED_HOSTS` for the name it's reached by. The browser can't change API keys here: it reaches the container through Docker's network, so Mivra treats it as remote (ADR-013). Pass keys with `-e`, or save one with `docker exec -i mivra mivra auth set openrouter`, which reads it from stdin. A container killed without a clean stop restarts normally.

To try the image before a release, run `npm pack` in `packages/mivra` with `--pack-destination ../../docker`, then `docker build -t mivra:test --build-arg MIVRA_PACKAGE=/tmp/context/okhay-p-mivra-<version>.tgz docker`.

## Native dependency

`better-sqlite3` ships prebuilt Node-API binaries inside its npm package, so `pnpm install` needs no compiler or Python and the binary doesn't depend on the exact Node version. `pnpm-workspace.yaml` ignores the package's install step, which would only run `node-gyp` and fail where it isn't installed.

| Platform | Binary | Tested here |
|---|---|---|
| Linux x64, glibc 2.34+ | yes | yes: install, query, on glibc 2.36 and 2.41; server tests on 2.41 |
| Linux x64, musl | yes | yes: install and query on Alpine |
| Linux arm64 (glibc 2.34+ or musl) | yes | no |
| macOS x64 and arm64 | yes | no |
| Windows x64 and arm64 | yes | no |

Other platforms have no binary, and glibc older than 2.34 can't load the one provided (it fails with ``version `GLIBC_2.33' not found``). `pnpm install` still succeeds there, and the server fails when it opens the database. To build from source, install Python, `make` and a C++20 compiler, then:

```sh
cd node_modules/.pnpm/better-sqlite3@*/node_modules/better-sqlite3
rm -rf prebuilds   # the loader prefers these over a local build
npx node-gyp rebuild --release
```

This worked on Debian 12 with g++ 12, taking over ten minutes, and failed on Ubuntu 20.04 with g++ 9.4, so on a system that old, upgrade instead. Reinstalling restores the prebuilds, so it has to be repeated afterwards. Building on macOS or Windows hasn't been tried.

## Access and security

- The server and the Vite dev server listen on `127.0.0.1` only.
- Every `/api` request except `/api/health` and `/api/doc` needs `Authorization: Bearer <token>`. The token is created on first start in `~/.mivra/auth-token` (mode 0600). The web UI gets it from a meta tag in `index.html`, injected by the server (production) or Vite (dev).
- The server rejects any `Host` that isn't loopback or listed in `MIVRA_ALLOWED_HOSTS`. This stops DNS-rebinding pages from reading the token.
- To use the UI from another device on your tailnet, proxy it instead of binding all interfaces: `tailscale serve --bg 5173` in dev, or `tailscale serve --bg 4096` plus `MIVRA_ALLOWED_HOSTS=<machine>.ts.net` in production.

For scripts: `curl -H "Authorization: Bearer $(cat ~/.mivra/auth-token)" http://127.0.0.1:4096/api/sessions`.

## Chat turns

Each reply is a *run* (`runs` table). A session has at most one running run, so a second send while a reply streams gets `409`. Message ids are single-use, so a retried request is rejected rather than generating twice. Completed replies are saved in full. Stop cancels the model call and records the run as `cancelled`; cancelled text remains visible after reload, artifact/tool parts are discarded and pending memories roll back. Stop targets the learner message id (`POST /api/sessions/{id}/stop` with `{ "messageId": "..." }`), so a stale request cannot cancel a later reply. Cancelled replies are excluded from later model context; provider errors are recorded as `failed` with the error. Runs left running when the server stops are marked `failed` on the next start.

Automatic quiz continuations run on the server even with no tab connected. `GET /api/sessions/{id}/continuation` replays the current run's redacted SSE chunks and then streams live chunks; disconnecting only detaches the subscriber. Its `x-mivra-continuation-stop-id` header supplies the unique run token to send as Stop’s `messageId`, so delayed cancellation cannot affect a later continuation. With no continuation running it returns `204` immediately, with a safe `x-mivra-continuation-error` header if the last continuation failed. The web client checks after an answer, session load, focus or visibility restoration, uses the normal chat state for streaming, and reconciles stored messages once at completion. It has no idle polling or periodic fallback.

## Learning artifacts

The agent shows interactive artifacts through tool calls (ADR-006): `show_algorithm_trace`, `show_code_walkthrough`, `show_composition`, `show_set_diagram`, `show_graph`, `ask_multiple_choice`, `ask_code_exercise`, `show_table` and `show_worked_steps`, registered by the first-party `core-learning` plugin (`packages/server/src/plugins/`) through the capability registry (ADR-007).

- Each tool call's input is validated against its `packages/protocol` schema and stored in `artifacts` with the full spec. Client output fails closed: the live stream and `GET /api/sessions/{id}/messages` pass only text, reasoning text and lifecycle parts plus `data-artifact` parts with the artifact's public view. Raw tool calls, provider metadata, sources and files never reach a client. Thinking streams into a collapsed disclosure: opening it may reveal answers mentioned by the model (ADR-006). Private artifact fields still stay on the server.
- `POST /api/artifacts/{id}/attempts` with `{ "answer": { "optionIndex": n } }` grades a check deterministically and returns the view with the grade. One attempt per check, accepted once the reply that asked it has finished.
- On later turns, each check's tool result tells the model whether the learner answered and how they did.
- The web UI renders `data-artifact` parts by kind (`packages/web/src/artifacts/`). Each part is validated against the protocol's `ArtifactView` first; anything that fails shows a "can't display this item" placeholder. Every stepped kind shares one stepper (prev/next, play/pause, arrow keys, and no controls for a single step), and at either end prev or next stays focusable, so the keyboard keeps its place. One polite live region in each announces the current step whole, whichever way the learner moved: its number, explanation, and what's otherwise only drawn, so steps with the same explanation aren't silent, and the visible counter is hidden from screen readers so it isn't said twice. A trace is that stepper over a sequence, and also announces which values the step changed. A trace may also carry its code (`code: { language, source }`, at most 40 lines of 120 characters and 4,000 characters in all), with each step naming the 1-based `lines` it highlights; the pane shows the code as inert text with line numbers, beside the values in a wide card and above them in a narrow one, and the live region reads the highlighted lines. A code walkthrough (#98) is that stepper over code that isn't about a sequence, such as a plain function or a React render: the same code pane, beside a Variables pane and an Output pane in a wide card and above them in a narrow one. Each step is a complete snapshot (highlighted lines, variables, plain-text output and an explanation), so a step with none shows "No variables at this step" and "No output yet", and stepping back shows exactly the earlier snapshot. The output is inert monospaced text that keeps its whitespace and scrolls in its own pane; the live region reads the highlighted lines, the variables and short output, and summarises long output by its line count. It is the tutor's illustration, never a run, and has no grader. A set diagram is a Venn diagram of 1 to 3 sets, stepped if it has steps; each region is computed as its exact shape, so a step can highlight any region, and what a region holds is measured against its exact space at the drawn size, re-measured on resize; what doesn't fit moves to a list below the diagram, leaving a marker such as `n = 30 ↓` or just `↓`. A count shows as `n = 7`, so it can't be mistaken for an element. A graph is drawn by the browser, never placed by the model: d3-hierarchy for a real tree when `kind` is `tree`, where an edge's optional `side` keeps a lone child to its left or right, and otherwise a d3-force layout run to the end once per graph, so it's deterministic and nothing moves while stepping. It's stepped if it has steps. Self-loops and parallel edges are drawn. Labels are HTML over the SVG and scale with it down to 11px, after which the graph scrolls in its own box, which then takes the arrow keys for scrolling and is a named tab stop. The layout estimates a label's size from its source and never measures it, so positions can't shift once fonts load; each label is clipped to that estimated box, so none can overlap another for being wider than estimated. Rendered labels are measured only to tell which were cut short: those are marked `…` and listed in full below the drawing, for sighted readers, as the screen-reader description already has them. A check posts the learner's choice and then shows the grade. After all checks in the latest reply are answered, the tutor continues automatically once, without a new learner message; sending a message first takes the place of that continuation. Its options stay disabled while the reply that contains it is still streaming, and once it has been answered. A table is a real `<table>` for truth tables and relation matrices: static, or stepped if it has steps, where changed cells persist and highlights last one step. Worked steps reveal a proof cumulatively, with a "Show all" control; only the current step is announced, and the earlier ones stay in the list to read. Only a check has anything to keep private.
- A composition draws its references as lines and glides its cards between steps (#114, `packages/web/src/artifacts/composition-stage.ts`). Both sit on top of the snapshot the stepper picked and never change it. `composition-geometry.ts` routes each line through the gaps between cards and leaves it out if it would cross a card or heading, or if the grid is under 452px wide; every reference keeps its chip either way. Only Prev, Next and the arrow keys glide (FLIP with the Web Animations API). Seeking, Restart, Home, End and reduced motion cut to the step, and a new step or a change in width cancels a glide that is still running.

## Code exercises

`ask_code_exercise` gives the learner a single-file JavaScript (issue #119) or Python (issue #120) exercise (ADR-016): instructions, starter code, a reference solution and 1 to 20 test cases. A **call case** calls `functionName` with a JSON array of arguments and compares the return value as JSON, ignoring object key order (`undefined` matches only itself). A **stdio case** runs the whole program with the case's input and compares what it printed: in JavaScript the input is the global `stdin` string and `readLine()` (the next line, or `null`) and output is `console.log`; in Python they are `input()`/`sys.stdin` and `print()`. Printed output is compared after normalising line endings to `\n` and dropping trailing spaces and tabs on each line and trailing blank lines; leading whitespace counts. `console.error`, `console.warn` and Python's stderr are shown but not compared. In Python a call case's arguments come from `json.loads` and its return value goes through `json.dumps` (so `None` is `null` and tuples are lists; sets and NaN are refused), and `functionName` must be a Python identifier.

- **Checked at creation.** The tool's input carries no expected results. Before saving, the server runs the reference on every case (`src/exercises/reference-check.ts`) in a subprocess (`exercise-child.ts` for JavaScript, `python-child.ts` for Python, bundled as `dist/exercise-child.js` and `dist/python-child.js` in the npm package) with an empty environment and a 256 MB heap, killed after 10 s (90 s for Python, which has to start Pyodide) plus 5 s per case. What the reference printed or returned becomes each case's expected result. If it throws or hits a limit on any case, nothing is saved and the tool result tells the model why (`status: "rejected"`), so it can fix the reference or the cases and call again; in a lesson the section's slot stays open for the retry. Stopping the reply kills the subprocess.
- **QuickJS everywhere.** The server's check and the browser run each case through the same function (`runExerciseCase` in `packages/protocol/src/code-exercise-runner.ts`), so both see the same globals, output formatting and limits. Each case gets a fresh QuickJS instance and runtime: 2 s of run time (QuickJS's interrupt handler), 64 MB of WebAssembly memory, a 384 KB stack (recursion a couple of thousand levels deep), and 20,000 characters of output. QuickJS's own memory limit can't measure allocations in this build (it counts each block as 8 bytes), so the memory cap is the WebAssembly memory's `maximum`, passed in with `newVariant`'s `wasmMemory`. The code sees no DOM, network, timers, `require` or `process`: only standard JavaScript, `console`, `stdin` and `readLine()`.
- **Python in Pyodide.** `createPythonCaseRunner` (`packages/protocol/src/code-exercise-python.ts`) runs each case through one Python harness on the server and in the browser alike: a fresh namespace, stdin, captured stdout/stderr and recursion limit per case, with modules the code imported staying loaded. The time limit is Pyodide's interrupt check: the runner hands Pyodide an "interrupt buffer" that reads SIGINT once the case is past 2 s, so Python raises `KeyboardInterrupt` at every check from then on (code that catches it still stops). Between cases the buffer always reads SIGINT, so Python a case left to run later (a callback scheduled through `pyodide.webloop`) is interrupted as soon as it starts; the worker and the reference-check child swallow the error that leaves behind. A long call into C doesn't check, so the hard limits below still apply. Memory can't be capped (ADR-016). Python can't reach JavaScript: the runner removes the `js` and `pyodide_js` modules. Pyodide still hands Python JavaScript objects (`pyodide.ffi.to_js`), from which `.constructor.constructor` is `Function`, so each side also forbids running strings as code:
  - **Server:** `python-child.ts` runs under Node's permission model (`--permission`, reading only Mivra's code and the `node_modules` directories it and its dependencies are installed in; no writes, subprocesses, workers or addons) with `--disallow-code-generation-from-strings`, Pyodide's file system in memory only, and `fetch`, `WebSocket`, the global `require` Pyodide leaves behind and `process.getBuiltinModule` deleted. Pyodide calls `process.binding("constants")`, which the permission model refuses, so the child answers that one call itself while Pyodide loads. Run from source (tests and `pnpm dev`), the child goes through tsx, which also needs a loader thread (`--allow-worker`), no cache and the repository readable.
  - **Browser:** `python-exercise.worker.ts` loads Pyodide, then deletes `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `WebTransport`, `importScripts`, nested workers, `BroadcastChannel`, `caches` and `indexedDB` from the worker's global scope and its prototypes, and refuses to run if any is left. Exercise workers are built into `assets/exercise-workers/`, and the server sends them with `Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'` (`EXERCISE_WORKER_CSP` in `serve-web.ts`; Vite's dev server sends the same). Without `'unsafe-eval'`, a string can't become code, which also rules out `import()` of another site, the one network path that can't be deleted. `python-exercise.spec.ts` checks that learner code can't import `js`, open a URL or run a string, and that no request leaves Mivra.
- **In the browser** (`src/exercise.worker.ts`, `src/python-exercise.worker.ts`, `src/exercise-runner.ts`, `src/artifacts/CodeExercise.tsx`), cases run one at a time in a Web Worker that receives only the code and the case's input, never the API token or the expected results. The interrupt handler only runs between bytecode instructions, so a long native call can overrun 2 s: the page terminates the worker if a case takes over 5 s, reports a time limit for it, and starts a fresh worker for the next. Stop terminates the worker at once. Python loads slowly, so its worker sends `started` when a case begins and the 5 s limit runs from then; loading itself may take up to 120 s. While a loaded Python worker is idle the page pings it every second and terminates it if it doesn't answer within 5 s, so deferred code stuck in a long call into C can't keep it busy; a run sent to a loaded worker that doesn't start within 5 s restarts it the same way. Focusing a Python exercise's editor starts loading Pyodide early, and the first run says "Starting Python…" until it's ready. **Run** runs the visible cases and records nothing; **Submit** runs every case, hidden ones included, and posts `{ code, results }` to `POST /api/artifacts/{id}/attempts`. An unsubmitted draft is kept in the browser's local storage.
- **Graded on the server.** The server compares each reported result with the expected one (`gradeCodeExercise`), so hidden cases' expected results never leave it; the view carries only their inputs. The results come from the browser and aren't tamper-proof, which ADR-016 accepts for a local app. Like any check there is one attempt, it counts as evidence for its `concept`, it holds a lesson's Finish until submitted, and it starts the automatic continuation. On later turns the tutor sees the result, the learner's code (as data, up to 4,000 characters) and up to 5 failing cases with their input, expected and actual result. After submitting, the view carries the saved code and results, so a reload shows them without running anything.
- **Assets are bundled.** QuickJS's WebAssembly file (`@jitl/quickjs-wasmfile-release-sync`, 503 KB, 236 KB gzipped) is built into the web UI's assets, and the npm package installs the same module for the server. Pyodide (`pyodide`, pinned to the same version in `server`, `web` and `mivra`) is an npm dependency of the package, not part of the build: the server uses it for reference checks and also serves its five runtime files (`pyodide.mjs`, `pyodide.asm.mjs`, `pyodide.asm.wasm`, `python_stdlib.zip`, `pyodide-lock.json`; 13.5 MB, about 7 MB over the wire with gzip) at `/assets/pyodide-<version>/`. So there's one copy, and exercises work offline with nothing downloaded from elsewhere. **Size impact (#120):** the `@okhay-p/mivra` tarball is unchanged (2.9 MB packed, 8.2 MB unpacked); installing it now also fetches `pyodide` (6.5 MB download, 13.9 MB unpacked) and its dependency `ws` (0.15 MB). Starting Pyodide takes a second or two on a typical machine, but can take 15-20 s on a slow one, both for the server's reference check and for the learner's first run.

## Markdown and maths

`MathText` (`packages/web/src/MathText.tsx`) renders model-written text in one of two modes:

- `block`, for replies: GitHub-flavoured markdown with KaTeX maths, `$...$` inline and `$$...$$` display.
- `math`, for artifact text: a trace's title and step explanations, every label, element and variable in a set diagram, a graph's title, step explanations, node labels and edge labels, a check's question, option text, feedback and explanation, a table's title, headers, cells and explanations, and all worked-steps text. Only `$...$` is a formula and `\$` a dollar. Everything else is literal, including `$$`, so the options `2*3*4` and `234` stay different. For a large formula, start it with `\displaystyle`. A new artifact field that may hold an answer or a structured value should use this mode; explanatory prose may use `block`.

Concept labels, a trace's cell values, pointer names, range labels and variables, and a graph's variables and edge weights aren't passed through `MathText`, and learner messages stay plain.

A `$...$` is maths only if there's no whitespace just inside its dollars, no digit just after the closing one, and no backtick between them, and the first dollar after the opening one decides. So "costs $5 and $10" isn't a formula. In `block` mode, code and `\$` take precedence over a dollar. Raw HTML shows as text, images show their alt text and never load, and only `http`, `https` and `mailto` links work. A reply is rendered block by block, so a streamed delta only re-renders its last block; a block over 50,000 characters, or with absurdly deep nesting at its line starts or a run of more than 32 `[` outside code, shows as plain text with its code still in a box, and so does a block that fails to render. Other hostile nesting, such as `[a [a [a ` repeated thousands of times, isn't detected and renders slowly.

## Learner memory

Each turn's instructions include part of the learner's record across all sessions: up to 30 recently practised concepts, each with how many checks were answered, how many were right, and the latest result. It is calculated from the latest 1000 graded attempts and never stored separately, so older practice stops counting (ADR-009).

The model can also save goals, preferences and misconceptions with the `remember` tool. They save automatically, take effect only if the reply completes, and appear in the sidebar's Memory panel, where the learner can edit or permanently delete them. A misconception is linked to a graded wrong answer on the same concept when there is one, and otherwise counts as only an impression from chat. A memory written while a check in its session is unanswered could give the answer away, so until the check is answered its content is hidden from the panel and left out of other turns, though it can still be deleted. One reply can save at most 5 memories, and the newest 40 are included in each turn. What was said in the chat itself stays in that session's conversation, so deleting a memory doesn't remove it from there.

The panel's **Export to Obsidian** downloads the memories that aren't held, with the concepts, as notes for an Obsidian vault (see Imported notes).

Memories drawn from imported notes (basis `import`, see Imported notes) also appear in the panel, as `known` ("Known from your notes") or as goals and misconceptions, each naming the note it came from. The panel can show only those or only the others, and delete all of them at once (`DELETE /api/memories?basis=import`). The model sees them apart from the rest, after the learner's record and their other memories, as a claim ranked below graded answers: the newest 40, goals and misconceptions before `known`. So a large vault can't push out the 40 other memories.

## Imported notes

An Obsidian vault can be imported as read-only notes (ADR-014), with `mivra import obsidian <folder>`, from **Imported notes** in the web UI's sidebar, or the API: `POST /api/imports` with `{ name, files: [{ path, text }] }`, and `PUT /api/imports/{id}/files` with `{ files }` to re-import. Learners never edit notes; they change only when their vault is imported again. Notes, links and tags are stored and searchable, and matching excerpts reach the tutor each turn and each lesson as it's written.

- **The web UI** (`src/ImportsPanel.tsx`) lists imports with their note count and last update, re-imports or deletes one (after a confirmation), and starts a new one. Its main path is a folder picker (`<input webkitdirectory>`); `src/vault-files.ts` applies the CLI's rules in the browser: the picked folder's own name is dropped from each path and becomes the default import name, files under a dot-folder or starting with a dot are left out silently, anything not ending in `.md` is counted and left out, and every size is checked before a file is read. A file over 4,000,000 bytes is skipped as too long, and once the notes together pass 64 MB the import stops before reading anything. The JSON body's size is checked again before it's sent. Importing under a name that's taken re-imports that vault with `PUT`.
- **A .zip is the fallback** for browsers that can't pick folders, such as iOS Safari: `POST /api/imports/zip` (multipart, a `file` field and an optional `name` field that defaults to the zip's file name) and `PUT /api/imports/{id}/zip` (just `file`). The upload is read like a document's (`readUpload`, 64 MB, streamed and counted) and unpacked in the extraction subprocess with the same timeout and memory limits (`src/notes/vault-zip.ts`, through `runInChild`). A zip with more than 50,000 entries, an entry named with `..` or an absolute path, or a password is refused; only `.md` entries outside hidden folders are unpacked, into memory and never onto disk; symbolic links are skipped and reported, as are attachments; a note's declared size over 4,000,000 bytes skips it, and the declared sizes of all notes together over 64 MB or more than 10,000 notes refuse the zip before anything is unpacked, while yauzl checks each entry against its declared size as it unpacks. When every entry sits in one top folder (as zipping a vault folder gives), that folder is dropped; `__MACOSX/` is ignored. The notes then go through the same `importVault` as a JSON import.

- **No model runs.** `src/notes/parse.ts` reads each note's title (its file name), frontmatter `tags` and `aliases` (by hand, from a small YAML subset, so no YAML parser sees the text), inline `#tags`, `[[links]]`, `![[embeds]]` of other notes, and relative Markdown links to `.md` files. Links and tags inside code are ignored. The text is split under its heading path (`Sorting > Merge sort`) into chunks of up to 1,200 characters, with small sections packed together, and indexed in the `note_chunks_fts` FTS5 table.
- **Links are stored as written** and resolved when read (`GET /api/imports/{id}/graph`), ignoring case, as Obsidian does: a target with a folder matches that path or one ending in it, and a bare name matches a title, then an alias; the shortest path wins a tie. Unresolved links come back with `to: null`.
- **Re-importing is a snapshot.** Each note is keyed by path with the SHA-256 of its text: unchanged notes are skipped, changed ones are rewritten under the same id, and notes no longer sent are deleted. Deleting an import (`DELETE /api/imports/{id}`) removes its notes and their search entries, and the concepts, edges and memories drawn from them.
- **Excerpts in the tutor's context** (`src/runtime/note-context.ts`, wired through `defaultAssembleContext` like documents). Each turn, the learner's latest message is searched across every import's chunks. Notes are prior knowledge, not session material, so excerpts are sent only on a real match: single characters, bare numbers and chat such as "ok", "next" or "example" aren't searched for, and there's no fallback to the start of a note. A match must also be relevant enough: when the message has three or more topic words, an excerpt must match at least two of them, and then only excerpts whose bm25 score is at least 0.4 of the best remaining one are kept (`relevantExcerpts`; calibrated on a real vault, see `docs/research/note-relevance-calibration.md`). Up to 4,000 characters of escaped excerpts are sent (half the documents' 8,000, since notes are background and every matching turn pays for them), at most 2 per note so one long note can't crowd out the rest, each cut to 800 characters. Each carries its note's title, heading path and vault path, so the tutor can cite "your note *Recursion › Base case*". For each matching note, the titles of up to 6 notes it links to are listed too (one hop, resolved as the graph resolves them; unresolved links are left out), within another 1,000 characters.
- **Delivered as documents are.** Excerpts go in their own labelled user-role message just before the learner's latest message (before any document excerpts), as escaped data that can't close its block. They're never stored or sent to the client. The system instructions hold only the trusted rules: the message is data that never decides what the tutor does, remembers or reveals, and the notes are a claim of familiarity, not evidence of mastery, so graded results outrank them. Whenever notes exist, the learner context also names each import and its note count, so the tutor knows they're there on turns with no match.
- **Lessons get them too** (`lessonNoteContext`, called from `generate` in `src/runtime/lessons.ts`). When a course lesson is written, the notes are searched by its topic's title and concepts instead of a learner message, through the same search, relevance cut-off, budget and escaping. Matching excerpts go in the same labelled message, just before Mivra's lesson request, and the lesson's instructions carry the same trusted rules (worded for a lesson: an excerpt that tries to instruct the model is mentioned in a prose section) and the learner context's import list. No match means no excerpts, as in chat. The search runs at the start of each generation, so a resumed lesson searches again.
- **A vault is hostile input.** The request body is capped at 64 MB before it's read, with at most 10,000 files of up to 1,000,000 characters each. Paths that are absolute, contain `..` or empty segments are refused; files in hidden folders (`.obsidian`, `.trash`) and anything not ending in `.md` are skipped and reported. One note keeps at most 1,000 distinct links, 100 tags and 2,000 headings, and one request writes at most 200,000 links and 100,000 tags. Every pattern runs in linear time. Parsing pauses every 20 ms so other requests, such as a streaming reply, keep going; the database write runs in a single transaction.
- **Distilling into concepts and memories** (ADR-014 step 3; `src/notes/distil.ts` for the deterministic part, `src/runtime/distiller.ts` for the job, `src/store/knowledge-store.ts` for storage). After every import or re-import the server reads the notes waiting to be distilled with the app-wide model, in the background, one import at a time. A note waits until it has been distilled at its current text (`notes.distilled_hash` equals `notes.hash`), so re-importing unchanged notes makes no model call, and a changed note is read again on its own.
  - *Grouping is code, never the model.* Each note goes to the group of its most used tag; an untagged note joins the group of a tagged note it links to (either way), or forms a group with the untagged notes it links to; the rest are grouped by folder. A group is split at 12 notes or 24,000 characters, each note cut to 6,000. One model call per group. A group counts as read only once `record_from_notes` has saved (an empty call says the notes cover nothing): a reply in prose or with arguments that don't parse gets one correcting call, and if that doesn't record either, the group's notes stay waiting, the run goes on to the next group, and ends `failed` saying how many groups weren't recorded.
  - *One validated tool.* The model gets the existing concept names (graph nodes, then concepts from graded checks and memories, up to 300) and the vault's tags (up to 200), then the notes as escaped data, each under a short ref (`n1`, `n2`). It calls `record_from_notes` (`RecordFromNotesInput` in `packages/protocol/src/knowledge.ts`) with concepts, `prerequisite`/`related` edges and memories (`known`, `goal`, `misconception`), each citing refs. The server settles every name: an exact (`conceptKey`) or close-spelling match (plural, or one typo in a word of 5+ letters, two in 9+) to a concept named earlier in the call, a graph node, or a concept from checks or memories takes that name, so `#binary-search`, "Binary searches" and "binary search" are one node. A name matching nothing must match a vault tag or appear (or a close spelling) in the notes it cites, or it's rejected. Refs outside the group, edges whose ends aren't concepts, an edge from a concept to itself, and a `known` or `misconception` memory without a concept are rejected too; the rejections go back to the model, which gets one more call to correct them. A prerequisite contradicting an existing one is dropped. At most 5,000 concept nodes are kept.
  - *Stored with provenance.* `concepts` (unique `key`), `concept_sources` (concept × note) and `concept_edges` (one row per note that supports the edge; `related` is stored with the smaller id first) all point at notes, and memories drawn from notes have basis `import` and a `note_id`. `GET /api/concepts` returns every concept and edge with the ids of their notes. A `known` memory is saved once per concept per import; a repeat of what the learner said, or of what the same import already gave, is skipped. A repeat within the import is recorded as one more note supporting the memory (`memory_sources`, with that note's own sentence), so the memory moves to another supporting note when its own note is deleted or rewritten, and then says what that note said (unless the learner edited it, when their text stays), and goes only with the last one, without any note being read again.
  - *Snapshots.* Rewriting a note forgets what it yielded (its concept sources, edges, and memories the learner hasn't edited and no other note supports) and that it was ever distilled, so it's read again even if its text returns to one distilled earlier; deleting a note or an import removes them by cascade. A concept goes once no note lists it as a source and no edge touches it.
  - *Sharing the server.* Distilling runs in the server's process, so it yields to the event loop (as import parsing does) before each group, between validating a call's proposal and saving it, and between reading an import's notes and its links. Matching names and saving are kept cheap per group: names are split into words once per call, the memories compared for repeats are read once per call, and rows are written in batches. With an instant scripted model, a 1,000-note import (85 groups) used to hold the event loop in one block of ~27 s; it now turns it every ~30 ms (median), rarely over 60 ms, after a run's start, which still costs a few blocks of 0.2–0.8 s (reading the notes and their links, and the first call's cold start). A test (`distillation.test.ts`) checks the loop turns between groups with a model that answers at once.
  - *Progress and cancel.* `GET /api/imports/{id}/distillation` (also in each import's view as `distillation`) gives the status (`idle`, `queued`, `running`, `cancelled`, `failed`), the notes waiting, the groups done of this run, and the concepts and memories drawn so far. `DELETE` cancels after the current call; what was saved stays and the rest waits. `POST` resumes, for instance after a failure, a cancel or a restart (a restart doesn't resume by itself). The **Imported notes** panel shows this with a progress bar, Cancel, and Resume or Try again, polling while it runs. A failed call shows only Mivra's own error text.
- **The graph view** (ADR-014 step 4; `src/notes/graph-view.ts` on the server, `src/NotesGraph.tsx` in the web UI). **Graph** on an import in **Imported notes** opens it in the main pane. Many vaults have few links, so tags and concepts are nodes too, joined to the notes that carry or cover them, and unresolved links are ghost nodes. `GET /api/imports/{id}/graph/view` decides what's drawn: with at most 500 notes matching the tag and folder filters (a tag includes its nested tags), the whole graph; otherwise, or with `mode=local`, the notes within `depth` hops (1 to 3) of `focus`, where sharing a tag or concept is one hop, as a link is. Without a focus it's the best-connected matching note. Whatever the vault's size, a view holds at most 500 notes, 1,000 nodes and 5,000 edges, filled nearest first, and says when it's `truncated`; the local graph draws a tag or concept only where it joins two drawn notes or the focus. It also lists the 200 fullest tags and folders for the filters. `GET /api/imports/{id}/notes?q=` finds up to 20 notes by title or path, to centre on one. The browser places the nodes, as for the graph artifact: a d3-force layout run to the end once, deterministic, here with Barnes–Hut repulsion and a fixed budget of node-ticks, in a worker (`notes-graph.worker.ts`) so the page never stalls; the previous drawing stays until the new one is ready. Kinds differ by shape (dot, diamond, square, dashed ring), in theme colours only. Labels are HTML over the SVG; above 150 nodes only those of the selection and its neighbours are shown. The drawing scrolls, pans by dragging and zooms with its buttons. Each node is a named button and the drawing one tab stop: arrow keys move to the nearest node in that direction, Home to the focus, and a polite live region reads what the node connects to. Clicking a note, or Enter, selects it and opens it read-only in a side sheet, as plain text, with a button to centre the local graph on it.

- **Exporting to Obsidian** (ADR-014 step 5; `src/notes/vault-export.ts`, `src/notes/zip-writer.ts`). **Export to Obsidian**, in the Imported notes and Memory panels, downloads `GET /api/export/obsidian`: a zip of a `Mivra/` folder to unzip into the learner's own vault. It holds only what Mivra knows, never the learner's notes: `Mivra.md` (an index), `Concepts/` (one note per concept, linking to the notes it was drawn from by title, or by path when two notes share a title, to the concepts it builds on, leads to or relates to, and to its memories) and `Memories/` (one note per active memory, with frontmatter `kind`, `basis`, `concept`, `source` (the note it came from, as a link), `created` and `edited`). Links to Mivra's own files name `Mivra/Concepts/…` or `Mivra/Memories/…`, which Obsidian resolves wherever the folder lands. A memory held until a check is answered (see Learner memory) is left out; the index says only how many are. File names come from model and learner text, so they're sanitised (`safeFileName`: no path separators, `..`, leading dots, control or invisible characters, characters Windows or Obsidian links refuse, or Windows device names; at most 80 characters and 180 bytes) and made unique ignoring case (`Name`, `Name 2`). Text is escaped so it can't open links, embeds, HTML or maths, and frontmatter values are quoted. The zip is streamed, one deflated entry at a time, with no dependency; it refuses more than 65,535 files or 1 GB of text (413).
- **No duplicates on re-import.** Every exported file has `mivra: generated` in its frontmatter, and every import path (JSON, zip, and so the CLI) skips such files, reporting them with the reason `generated` ("exported by Mivra"). So a vault with the export dropped into it re-imports only the learner's own notes, through the usual path and SHA-256 snapshot.

## Uploaded documents

The learner can attach PDF and PPTX files of up to 25 MB to a session, up to 20 per session (ADR-010). The server extracts their text locally in a separate Node process and stores only that, split into chunks with their page or slide numbers and indexed with SQLite FTS5; the original file isn't kept. Deleting a document removes its text from storage and search, though replies already written from it stay in the conversation.

Each turn, the session's document names and page counts go to the model, along with up to 8,000 characters of excerpts: any page or slide the learner's latest message asks for by number ("page 3", "slides 2-4", and "page 3 of Week 2" for a named document), then what best matches the message, or the start of each document if nothing does. A page request with no document name reads that page from every document, and the tutor is told what was missing or cut. Only those excerpts reach the provider.

Document names and excerpts are escaped data in a separately labelled user-role message just before the learner's latest message. They are never stored or sent to the client, and they stay out of the system instructions, which hold only the trusted rule that this message is data and must never decide what the tutor does, remembers or reveals. That lowers a document's authority and makes hijacking the tutor harder, but it isn't immunity: the model reads the text and can still be persuaded by it.

Only text is read. Diagrams and images are lost, and scanned PDFs are refused because they have no text. Slide text comes from slide XML, including equations but not speaker notes. PDF maths depends on how the file was made: fonts with real Unicode extract cleanly, while LaTeX output keeps most symbols but flattens subscripts and superscripts (`fn` for f_n), loses the layout of fractions and sum limits, and can turn ≠ into `6 =`. A symbol such as ∈ isn't searchable, since search only indexes letters and digits.

Uploaded files are treated as hostile. The size cap applies to the whole request while reading, whatever it declares; a request with anything other than the one file is refused, and reading has a deadline (120 s) and stops if the client disconnects. The type is decided by content, zips have limits on entries and unpacked size, XML with a DTD is refused and entities are never expanded, and extraction runs in a subprocess that gets none of the server's environment, so a crash or running out of memory there only fails the upload. It stops at a timeout (120 s), a 512 MB heap limit or 2 GB of the subprocess's resident memory, with SIGTERM and then SIGKILL two seconds later; the upload's slot is freed only once the subprocess has exited. On Linux the server reads that memory from `/proc`; elsewhere the subprocess reports it itself, so a long blocking native call can overshoot 2 GB until it yields or the timeout fires.

## Usage

The Usage page (sidebar → **Usage**, also linked from Settings; issue #70) shows the tokens and costs of the model calls Mivra makes. It counts only Mivra's own calls from when tracking started, never account-wide usage or a plan's remaining allowance: for ChatGPT plan limits it links to ChatGPT's own usage settings, and there is no limits view.

- **Recording.** `src/usage/tracker.ts` is AI SDK language-model middleware, added inside `containStreamErrors` on every `streamText` call: chat turns (`chat`), automatic continuations (`continuation`), lesson generation (`lesson`), background note distillation (`distillation`, with no session; one run per group of notes) and a custom provider's Test model (`test`). Each provider call is one row in `usage_records`, so a reply with tool-call steps has several and a retried call has one per attempt. A call is recorded once, when its stream finishes, fails or is cancelled. Tokens come from the provider's finish part; a call that never sent one (a failed or cancelled call) is stored with null counts, which the page shows as unknown, never zero. A new kind of model call must pass `usage.middleware(...)` too.
- **Content-free.** A row holds the kind, status, session and run ids (plain text with no foreign keys, so deleting a chat keeps its usage), provider and model ids with their display names as they were, token counts, the price and costs. Never prompts, replies, error text or credentials. Session titles are read live when the page asks; a deleted session shows as "Deleted chat".
- **Tokens.** Input includes cached input (`cacheRead`, `cacheWrite`) and output includes reasoning, so those are shown as parts and never added again. Sums cover the calls that reported them, and the page says how many didn't.
- **Money, in separate buckets.** API spending is OpenRouter's reported `usage.cost` when there is one, otherwise an estimate from the price snapshot: the learner's custom price (Usage → Advanced, `usage.prices` in settings) or the catalog's price, including OpenRouter's cached-input rate. Cached tokens with no cached rate listed make the estimate unknown rather than overstated. The snapshot and estimate are stored with the call, so later price changes never rewrite history. ChatGPT plan calls are subscription usage: their estimate at the API counterpart's published price (`apiPrice` in the catalog) is only shown as an optional "Estimated API equivalent", never added to spending.
- **API.** `GET /api/usage?from=&tz=` returns the totals and breakdowns by provider, model, kind, session, run and local day; `DELETE /api/usage` clears the records only; `PUT /api/usage/prices` sets or removes a custom price.

## Web UI

The UI uses [shadcn/ui](https://ui.shadcn.com) with the Paper & Amber theme (ADR-008). Components are copied into `packages/web/src/components/ui`, and theme tokens live in `src/styles.css`. To add a component, run `pnpm dlx shadcn@latest add <name>` from `packages/web`, then check that it didn't overwrite the tokens in `styles.css`, and point any `from "cn"` import at `@/lib/utils`. Fonts are bundled through `@fontsource`, so the app needs no network for them. The theme follows the OS until the learner picks Light or Dark in the sidebar; the choice is saved in the browser.
