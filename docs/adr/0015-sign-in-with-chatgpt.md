# ADR-015: Sign in with ChatGPT through OpenAI's open-source route

**Context:** ADR-012 deferred "sign-in with a ChatGPT subscription via OAuth" until OpenAI permitted third-party apps to use subscription credentials. OpenAI now documents [Sign in with ChatGPT](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt) with a token-sharing route for open-source and personal local projects: a learner with an eligible Plus or Pro plan signs in, and the app calls the Responses API on `https://api.openai.com/v1`, billed to their plan instead of an API key. Hosted and paid apps need a waitlist; Mivra is open source, MIT-licensed and runs on the learner's machine (ADR-001), so it qualifies for the open-source route. The protocol is public OAuth 2.0 with PKCE: a dynamic first-time registration (`client_id=dynamic_agent_client`) issues a per-account client id, the redirect goes to a loopback listener on `127.0.0.1`, and the token response carries a rotating refresh token (30 days) and a one-hour access token. The app must request the `chatgpt.tokens.use.direct` scope and check it was granted. Every inference request must set `store: false` and `stream: true`; `previous_response_id`, `temperature`, `max_output_tokens`, `metadata` and system-role messages are rejected. Function tools are supported, which Mivra's learning tools need. OpenAI's DevKit (`openai/sign-in-with-chatgpt-devkit`) wraps the flow, but it isn't published to npm and its code is under a noncommercial licence that doesn't fit an MIT project.

**Options:**

- Client: (A) vendor or depend on the DevKit; (B) implement the documented protocol in Mivra; (C) run the Codex app-server and talk to it.
- Where the credentials live: (1) `credentials.json` next to the API keys; (2) a separate `chatgpt.json` in the data dir; (3) the database.
- Who signs in: (i) the UI only; (ii) the UI and `mivra auth`.

**Decision:** (B), (2) and (ii).

- **Own implementation of the documented protocol** (`packages/server/src/chatgpt/`). Written from OpenAI's protocol pages, not copied from the DevKit. Endpoints come from `https://auth.openai.com/.well-known/openid-configuration`, which must name that issuer and keep every endpoint on its origin. The ID token is checked with Node's crypto against the published JWKS (RS256, issuer, audience = the issued client id, expiry, nonce), so no JWT library is added. Sign-in fails unless the granted scopes include `chatgpt.tokens.use.direct`.
- **A ChatGPT provider in the model registry.** Model ids are `chatgpt:<slug>`, resolved through the AI SDK's OpenAI Responses model pointed at `https://api.openai.com/v1`, with a fetch that sets a fresh access token on each request and drops organisation and project headers. Every ChatGPT call sends `store: false` and developer-role instructions; Mivra already streams every model call. Without stored responses, reasoning is replayed through encrypted reasoning content, which the SDK requests when `store` is false. `OPENAI_BASE_URL` doesn't apply: the token must only ever go to OpenAI.
- **Catalog.** When signed in, the picker lists the models `GET /v1/models` returns with `visibility: "list"`, named by their `display_name`. Each is described (context length, effort levels) by its OpenRouter counterpart `openai/<slug>` when there is one, like the direct providers in ADR-012; it has no per-token price, since the plan pays. The plan offers a short list, so unlike ADR-012's search-only catalog the picker shows every ChatGPT model under "ChatGPT plan" without searching. The built-in default prefers ChatGPT when signed in, since signing in is an explicit choice that costs nothing extra.
- **Credentials in `chatgpt.json`,** mode `0600`, written atomically, out of `mivra.db` like the API keys (ADR-013). It holds a host id (`urn:uuid:…`, made once and sent as `ext_agent_host_id`), the issued registration (client id, account subject, email) and the session tokens. Signing out revokes the refresh token and deletes the tokens but keeps the registration, so signing in again reuses the same client id instead of registering another app. "Use a different account" starts a fresh registration. Tokens never reach a client, logs or the database: clients get a view (signed in or not, the account's email, any notice).
- **Refresh.** An access token with under five minutes left is refreshed before a run, one refresh at a time; the rotated refresh token is saved before anything else can fail. A terminal refresh error (`invalid_grant` and its kin) clears the session and asks the learner to sign in again. A usage-limit error (`subscription_sharing_usage_limit_exceeded`) is shown as such, with a pointer to ChatGPT's usage settings, and isn't retried.
- **Sign-in from any allowed client, unlike API keys.** ADR-013 keeps key changes to loopback clients; the ChatGPT sign-in is open to any client the host guard and auth token let in, such as a browser on the learner's tailnet. Tokens still never leave the server, and the code in a callback is useless without the PKCE verifier that stays on the server. The server listens for the callback on `127.0.0.1:1455` (any free port if that's taken) for ten minutes; the callback must carry the pending state. When the browser isn't on the server's machine (a tailnet browser, Mivra in Docker), ChatGPT sends it back to its own `127.0.0.1`, which fails; the learner pastes that address into the panel and Mivra finishes from it. `mivra auth login chatgpt` runs the same flow from the terminal (opening the browser, or printing the address with `--no-open`, and accepting a pasted address), `mivra auth logout chatgpt` signs out, and `mivra auth status` shows the account. So a Docker or VPS install can sign in from its web UI or with the CLI through `docker exec` or SSH.
- **OpenAI's UI guidelines.** The sign-in button is the approved "Continue with ChatGPT" format (black with the white ChatGPT mark, white with the black mark in dark mode), and the settings row uses the guidelines' wording ("Use your ChatGPT plan", "Reconnect to ChatGPT", "Connected", "Disconnect"). While the selected model is a ChatGPT one, "Using ChatGPT plan" with a "Manage usage" link to `chatgpt.com/settings/usage` sits beside the model picker. A usage-limit failure shows "Usage limit reached" with "Manage usage" as the primary action. The first sign-in ever shows the one-time "You're using your ChatGPT plan" dialog; `chatgpt.json` records that it was shown. The ChatGPT mark comes from OpenAI's approved button assets and is used only there, under OpenAI's brand guidelines.

**Consequences:** Learners with a ChatGPT plan can use Mivra without an API key. Mivra depends on a preview programme whose rules may change: its endpoints, scopes and rejected fields are kept in one module, and a request OpenAI starts rejecting fails with a clear message rather than silently. Mivra can't use features the route rejects (server-side response storage, sampling settings, output caps). Plus users share a five-hour usage limit across every app on their plan. OpenAI doesn't tell apps when a learner disconnects them in ChatGPT's settings; Mivra finds out from the next failed refresh. A second credential file now sits in the data dir, protected by file permissions only, like the keys.

**Build order:**

1. Protocol module, credential file, token refresh and the ChatGPT provider and catalog (server, with tests against a fake authorization server).
2. Routes and the ChatGPT row in Settings → Model providers, with paste-the-address fallback; first-run onboarding counts a ChatGPT sign-in as a provider.
3. `mivra auth login|logout chatgpt` and the status line.
4. A live check with a real Plus or Pro account before release: tool calls, multi-turn reasoning replay, usage-limit errors.
